# 버전 보고서 쓰기

**태그를 찍는 모든 버전에 쓴다. PATCH도 쓴다.** 예전에는 MINOR 이상만 썼는데,
그러면 PATCH 구간의 지표가 다음 MINOR에 섞여 무엇 때문에 움직였는지 못 읽는다.

| | 절 | 분량 |
|---|---|---|
| MAJOR · MINOR | 1~6절 전부 | 제한 없음 |
| PATCH | 2 · 3 · 6절 | 한 쪽 |

PATCH에서 하네스를 안 바꿨으면 **"안 바꿨다"고 적는다.** 규칙을 매번 늘리는 것이
목적이 아니고, 안 바꾼 것도 판단이다.

## 최종 목표는 토큰이다

하네스를 고치는 이유는 **같은 결론에 토큰을 덜 쓰고 도달하기 위해서**다. 재작업을
줄이는 것도, 시뮬레이터를 닫은 것도, 되묻는 것도 전부 그리로 간다.

그래서 모든 보고서는 **M12 프롬프트당 토큰이 어디로 갔는지**로 판정을 마무리한다.
M1이 내려가고 M3이 내려가도 M12가 올랐으면 그 하네스는 실패로 적는다. 지표를
좋게 만드느라 비용을 키우는 하네스가 실제로 있었다 — 옛 R2가 그것이다.

| | v1.0.0 | v1.1.0 |
|---|---:|---:|
| M12 프롬프트당 토큰 | 17,093,692 | 31,109,720 |

**성분을 같이 읽는다.** 캐시 읽기가 압도적이고, 그건 컨텍스트가 얼마나 부풀어
있었나에 비례한다. 어떤 행동이 비쌌는지는 그 행동의 턴이 아니라 **그 뒤 모든 턴**에
나타난다.

## 이 보고서는 무엇에 관한 것인가

**하네스에 관한 것이다.** 지표에 관한 것이 아니다.

매 절의 주어가 하네스여야 한다 — 무엇이 적용돼 있었고, 어떻게 작동했고, 뭐가
부족했고, 그래서 뭘 바꿨고, 뭘 기대하는가. 지표는 "작동했는가"를 판단하기 위한
**증거**로만 등장한다. 지표를 나열하고 끝나면 그 보고서는 실패한 것이다.

판단 기준 하나: **읽고 나서 `CLAUDE.md`가 안 바뀌면 그 보고서는 쓸 이유가 없었다.**

## 규칙을 만들 때 반드시 하는 대조

v1.1.0 보고서가 여기서 실패했다. 사용자 요청을 **인용까지 해놓고 반대 규칙을 만들었다**
— "시뮬레이터 쓰지 마"를 옮겼더니 "쓰되 판정만 넘겨라"가 됐고, 같은 요청이 세 번째로
올 때까지 아무도 못 잡았다.

규칙 하나를 쓸 때마다 표를 만든다. 세 열이 서로 안 맞으면 규칙이 틀린 것이다.

| 사용자가 한 말 (원문 그대로) | 만든 규칙 | 같은 것을 말하는가 |
|---|---|---|
| "시뮬레이터 사용은 나한테 부탁해주고 사용하지 마" | R2 시뮬레이터 금지 | ○ |
| ~~같은 말~~ | ~~R2 바꾼 화면 직접 확인~~ | ✕ 반대다 |

- **원문을 요약하지 않는다.** 요약하는 순간 해석이 들어간다.
- **AI의 편의를 근거로 요청을 뒤집지 않는다.** v1.1.0은 "새벽 작업 속도"를 근거로
  뒤집었다. 속도가 이유가 되려면 사용자가 그 교환을 선택해야 한다 — 물어보면 된다.
- **같은 요청이 두 번 이상 나왔으면 규칙이 아니라 강제 장치를 고민한다.**
  문서는 잊히고, 권한 설정(`.claude/settings.local.json`)은 안 잊힌다.

## 비용도 지표다

v1.2.0부터는 **지표를 얼마에 샀는지**를 같이 본다. 하네스가 지표를 좋게 만들면서
비용을 키우면 그건 성공이 아니다.

- M11 시뮬레이터 호출 수 — 목표 0. PR 스크린샷은 빼고 읽는다
- `edits` · `builds` · `test_runs` — 같은 결론에 몇 번 만졌나
- 폐기된 옛 R2가 정확히 이 함정이었다. M1을 낮추려고 도구 호출 1,015회를 썼다

## 절 구성 — 바꾸지 않는다

버전 간 같은 자리에 같은 것이 있어야 비교된다.
**제목은 대화체로 쓰지 않는다** — 목차만 훑어도 무슨 절인지 알 수 있는 명사형으로.

```
1. 보고서 개요                    목적 / 구성 / 대상·원본 / 요약
2. 이전 사용 결과                 적용돼 있던 하네스 → 하네스별 성적 → 전체 지표
3. 결과 분석                      지표 해석 → 원인(구멍마다 "필요한 것"으로 끝)
4. 추후 사용될 하네스와 그 이유     규칙 / 절차 / 문서 / 주요 설계 판단
5. 기대효과                       지표별 목표 → 성패 판정 기준 → 다음 확인 항목
6. 비용과 구성                    토큰이 어디로 갔나 / 모델 구성 / 서브에이전트 구성
부록. 지표 정의와 한계
```

6절은 2026-08-18에 추가됐다. 앞의 다섯 절이 "무엇을 얼마나 잘했나"라면
6절은 **"얼마에 샀나, 그리고 다음엔 무엇으로 살 것인가"**다.

`docs/harness/reports/v1.1.0.md`가 기준 형식이다. 소절 제목도 명사형으로 쓴다
("무엇이 부족했나" ✕ → "원인 — 다섯 가지 구멍" ○).

## 절별로 쓰는 법

### 2.1 — 적용돼 있던 하네스

**"하네스가 없었다"고 쓰지 않는다.** 거의 항상 뭔가는 있다. v1.1.0을 쓸 때도 처음엔
"없었다"고 썼는데, 확인해보니 커밋 규칙과 디자인 규범이 개발 첫날부터 있었다.
없던 건 하네스가 아니라 **그걸 읽게 만드는 진입점**이었고, 그게 진짜 진단이었다.

각 문서가 언제 생겼는지 확인한다:

```bash
git log --diff-filter=A --format='%ad' --date=short -- <파일> | tail -1
git cat-file -e V<이전버전>:<파일> && echo "그때 있었음"
```

**지켜졌는지**를 반드시 적는다. 있는 것과 작동한 것은 다르다. 문서에만 있고 한 번도
안 쓰인 규칙이 가장 위험하다 — 나머지 규칙까지 같이 신뢰를 잃는다.

세션 중 구두로만 요청되고 기록되지 않은 규칙이 있으면 그것도 적는다. 그게 다음 버전
하네스의 가장 좋은 후보다.

### 2.2~2.3 — 성적과 지표

먼저 하네스별 성적표(2.2), 그 다음 전체 지표표(2.3). 순서를 바꾸지 않는다 — 지표를 먼저 놓으면
독자가 왜 이 숫자를 보는지 모른 채 읽게 된다.

```bash
python3 tools/harness_report.py --version 1.2.0 --append
```

숫자를 손으로 고치지 않는다. 이상하면 스크립트 정의를 보고, 정의가 틀렸으면 `SCHEMA`를
올리고 **이전 버전 전체를 다시 돌려** 원장을 재생성한다. 한 버전만 새 정의로 재면
그 순간 추세가 거짓말이 된다.

판정:

| 판정 | 조건 |
|---|---|
| **효과** | 담당 지표가 의도한 방향으로 |
| **무효** | 반대거나 변화 없음. 두 번 연속이면 폐기 |
| **미확인** | 프롬프트 50개 미만. 우연이 실력처럼 보이는 구간 |
| **미측정** | 데이터가 안 쌓였다. **무효와 반드시 구분한다** |

미측정을 무효로 읽고 규칙을 지우면 효과 있었을 규칙을 잃는다.

지표가 좋아졌다고 규칙 덕이라 단정하지 않는다. 버전 성격 때문일 수 있다 — 다른 설명이
있으면 같이 적는다.

**"어떻게 읽었나" 소절을 반드시 쓴다.** 숫자 두 개가 같이 움직인 이유, 예상과 어긋난
지표. 여기가 3.2 진단의 재료가 된다.

### 3 — 결과 분석

구멍 하나에 한 소절. 각 소절은 **`→ 필요한 것:`** 한 줄로 끝난다. 그 줄이 4절의
입력이다.

증상이 아니라 **왜 루프가 안 닫혔는지**를 쓴다. 기술적 원인은 `docs/TRAPS.md`로 가고,
보고서에는 "무엇이 그 판단을 어렵게 만들었나"가 남는다.

M5 최다 주제가 힌트다 — 시간을 가장 많이 먹은 곳이 대개 구멍이 있는 곳이다.

### 4 — 추후 사용될 하네스

**3.2의 구멍과 1:1로 대응해야 한다.** 대응 안 되는 변경이 있으면 근거 없이 문서를 늘린
것이고, 대응 안 된 구멍이 있으면 진단해놓고 안 고친 것이다. 둘 다 적어야 한다
(안 고쳤으면 왜 미뤘는지).

각 규칙 행에 "대응 구멍" 칸을 두고 3.2의 번호를 적는다.

지표를 붙일 수 없는 것은 **규칙이 아니라 스킬이나 함정 문서로** 넣는다. 규칙은 짧아야
읽힌다.

**지켜지지 않던 규칙을 지우는 것도 변경이다.** 폐기는 실패가 아니라 성과다.

### 5 — 기대효과

지표별로 `기준 → 목표`와 **기대하는 이유**를 쓴다. 이유가 안 써지면 그 규칙은 근거가
약한 것이다.

목표치는 추정이 아니라 출발점이다. 두 버전 쌓이면 조정하고, 조정 사실을 원장에 남긴다.

### 6 — 비용과 구성

앞의 다섯 절이 "무엇을 얼마나 잘했나"라면 여기는 **"얼마에 샀나"**다. 세 소절이다.

#### 6.1 토큰이 어디로 갔나

M12와 성분 넷을 표로 놓고, **이번 버전에서 가장 비쌌던 행동 하나**를 지목한다.
"토큰을 많이 썼다"로 끝내지 않는다 — 무엇이 컨텍스트를 부풀렸는지까지 간다.

```bash
python3 tools/harness_report.py --version 1.2.0 --to HEAD
```

출력의 `토큰 성분`·`도구 상위` 두 줄이 재료다. 도구 상위에서 1위가 무엇인지가
대개 답이다 (v1.0.0·v1.1.0에서는 둘 다 시뮬레이터였다).

#### 6.2 모델 구성

M13과 모델별 턴 수를 놓고 **다음 버전에 무엇을 어디에 쓸지 제안**한다.

| 작업 성격 | 제안 | 근거 |
|---|---|---|
| 파일 찾기 · 목록화 · 기계적 치환 | 하위 모델 | 판단이 없다 |
| 규범 해석 · 설계 판단 · 되묻기 | 상위 모델 | 잘못 판단하면 재작업이 토큰을 더 먹는다 |
| 넓은 조사 | 하위 모델 **서브에이전트** | 결과가 본 컨텍스트에 안 쌓인다 |

**"싼 모델을 더 쓰자"로 끝내지 않는다.** M13이 내려간 버전에서 M1이 올랐으면
잘못 내린 것이고, 그 조합을 표로 남겨야 다음에 같은 실수를 안 한다.

#### 6.3 서브에이전트 구성

**이 소절의 목적은 다음 버전의 위임 구성을 정하는 것이다.** 그래서 M14 숫자보다
아래 목록이 본체다.

| 모아야 할 것 | 어디서 나오나 |
|---|---|
| 위임했으면 쌌을 지점 | R9에 따라 답 끝에 남긴 "여기는 위임했으면 쌌다" 줄 |
| 그 지점의 성격 | 조사인가 / 판단인가 / 반복 작업인가 |
| 한 번에 오간 컨텍스트 크기 | 그 구간의 `Read` 수와 검색 폭 |

그걸 모아 **에이전트 후보를 표로 낸다.** 이름 / 무슨 일 / 어떤 모델 / 왜 분리하나.
후보가 없으면 "이번 버전에는 위임할 만한 덩어리가 없었다"고 적는다 — 억지로
만들지 않는다. 위임은 **설명 비용이 직접 하는 비용보다 작을 때만** 이득이다.

M14가 0인 채로 두 버전이 지나면 R9를 재검토한다. 규칙이 실행 불가능한 것인지,
아니면 위임할 일이 실제로 없는 프로젝트인지 판단해서 원장에 적는다.

## 위키에 올린다

원본은 `docs/harness/reports/v<버전>.md`, 위키는 사본이다.

```bash
git clone https://github.com/Mosco-KR/Mosco-iOS.wiki.git /tmp/wiki
cp docs/harness/reports/v1.2.0.md /tmp/wiki/AI-사용-보고서-v1.2.0.md
# Home.md 의 보고서 목록에 줄 추가
cd /tmp/wiki && git add -A && git commit -m "AI 사용 보고서 v1.2.0" && git push
```

위키 페이지 이름이 곧 URL이다. `AI-사용-보고서-v<버전>` 형식을 지킨다.
`Home.md`의 보고서 목록에 새 줄을 더한다. 공개 문서이므로 올리기 전에:

- 절대 경로에 사용자 이름이 없는지
- 시뮬레이터 UDID, 기기 식별자, 계정 정보가 없는지
- 인용에 짜증·비속어 표현이 없는지 (판단이 담긴 인용만 쓴다)
