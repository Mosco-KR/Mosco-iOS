# 하네스

AI와 함께 일하는 방식을 **측정하고, 규칙을 세우고, 그 규칙을 채점해서 고치는** 체계.

**최종 목표는 토큰이다** — 같은 결론에 토큰을 덜 쓰고 도달하는 것. 재작업을 줄이는
것도, 시뮬레이터를 닫은 것도, 되묻는 것도 전부 그리로 간다.

## 왜

Mosco는 대부분 AI와 함께 만들었다. 그렇게 만들다 보면 같은 말을 두 번 세 번 하게 되는
구간이 생기는데, 어디서 왜 그러는지는 느낌으로만 알 수 있었다. 느낌으로는 무엇을
고쳐야 할지 정할 수 없다.

그래서 세션 기록과 git에서 지표를 뽑아, 작업 규칙 하나하나가 실제로 재작업을 줄였는지
버전마다 채점하기로 했다.

## 구성

```
tools/harness_report.py     지표 추출. 정의가 여기 얼어 있다
docs/harness/
  metrics.tsv               버전별 지표 한 줄씩
  rules.md                  규칙 원장 — 도입 시점, 담당 지표, 채점 이력
  verify-log.tsv            사람 검증 결과 pass/fail
  reports/v<버전>.md         버전별 보고서
CLAUDE.md                   규칙 본문 (AI가 매 세션 읽는다)
```

## 한 바퀴

보고서는 지표 모음이 아니라 **하네스의 변경 이력과 그 근거**다. 매 절의 주어가
하네스다.

```
릴리스 (PATCH 포함 전 버전) → git tag → 지표 추출
   │
   ├─ 1. 적용돼 있던 하네스가 무엇이었나
   │        있던 것 / 언제부터 / 실제로 지켜졌나
   │
   ├─ 2. 그게 어떻게 작동했나
   │        규칙별 판정 ← 지표는 여기서 증거로만 등장
   │
   ├─ 3. 무엇이 부족했나
   │        구멍마다 "→ 필요한 것:" 한 줄로 끝낸다
   │
   ├─ 4. 그래서 이렇게 바꿨다
   │        3절 구멍과 1:1 대응. 대응 안 되면 근거 없는 변경이다
   │
   ├─ 5. 기대 결과
   │        지표별 목표 + 성공·실패 판정법
   │
   └─ 6. 비용과 구성
            토큰이 어디로 갔나 / 모델 구성 / 서브에이전트 구성
            │
            └─→ CLAUDE.md 갱신 → 다음 버전 2절에서 채점
```

**PATCH도 보고서를 쓴다.** 안 쓰면 그 구간 지표가 다음 MINOR에 섞여 무엇 때문에
움직였는지 못 읽는다. PATCH는 2·3·6절만, 한 쪽이면 된다.

**읽고 나서 `CLAUDE.md`가 안 바뀌면 그 보고서는 쓸 이유가 없었다.**

절차는 [`/report`](../../.claude/skills/report/SKILL.md) 스킬에 있다.

## 두 가지 원칙

**하나. 채점할 수 없는 규칙은 넣지 않는다.**
담당 지표가 없으면 효과를 알 수 없고, 효과를 모르면 문서는 계속 늘고, 늘어난 문서는
아무도 안 읽고, 안 읽히는 문서는 규칙이 아니라 장식이다. 절차가 필요하지만 채점할 수
없는 것은 규칙이 아니라 스킬로 넣는다.

**둘. 정확한 정의보다 안 바뀌는 정의가 낫다.**
지표 정의는 노이즈를 품고 있다. 그래도 버전마다 같기만 하면 노이즈도 같은 크기로
들어가므로 추세는 살아 있다. 정의를 고치면 그 순간 이전 버전과 비교가 끊긴다 —
고쳐야 하면 스키마를 올리고 전체를 다시 돌린다.

## 베이스라인

스키마 3 기준이다 (M12~M15를 넣고 M8 오탐을 제거하면서 전체를 다시 돌렸다).

| | v1.0.0 | v1.1.0 |
|---|---|---|
| 재지시율 | 31.1% | 44.8% |
| 빌드 실패율 | 12.0% | 20.6% |
| 규범 드리프트 | 4 | 4 |
| **시뮬레이터 호출** | **1,015** | **716** |
| 회귀 테스트 | 0 | 0 |
| **프롬프트당 토큰** | **17.1M** | **31.1M** |
| 위임 비중 | 0% | 0% |
| 프롬프트 | 180 | 29 |

v1.1.0이 나빠진 것은 실력이 아니라 작업 성격 때문이다 — 시뮬레이터로 확인할 수 없는
영역(라이브 액티비티, 다이나믹 아일랜드)에 3일을 썼다. 자세한 것은 보고서에.

시뮬레이터 호출 1,015회와 716회는 **테스트가 0개인 채로 치른 비용**이다. 프롬프트
하나당 v1.0.0은 5.6회, v1.1.0은 24.7회를 썼다.

그리고 그 비용이 어디에 나타났는지가 프롬프트당 토큰이다. 두 버전 모두 **캐시 읽기가
전체 토큰의 97%**인데, 이건 "컨텍스트에 무엇을 들였나"가 아니라 **"들인 것을 몇 번
다시 읽었나"**다. 스크린샷은 찍은 턴에만 비싼 게 아니라 세션이 끝날 때까지 모든 턴에
다시 실린다.

v1.2.0의 목표는 시뮬레이터 칸이 0이 되고, 회귀 테스트 칸이 0이 아니게 되고,
프롬프트당 토큰이 절반 이하로 내려가는 것이다.
