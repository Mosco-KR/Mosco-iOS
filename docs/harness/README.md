# 하네스

AI와 함께 일하는 방식을 **측정하고, 규칙을 세우고, 그 규칙을 채점해서 고치는** 체계.

## 왜

Mosco는 대부분 AI와 함께 만들었다. 그렇게 만들다 보면 같은 말을 두 번 세 번 하게 되는
구간이 생기는데, 어디서 왜 그러는지는 느낌으로만 알 수 있었다. 느낌으로는 무엇을
고쳐야 할지 정할 수 없다.

그래서 세션 기록과 git에서 지표를 뽑아, 작업 규칙 하나하나가 실제로 재작업을 줄였는지
버전마다 채점하기로 했다.

## 구성

```
tools/harness_report.py     지표 추출. 정의가 여기 얼어 있다
docs/harness/
  metrics.tsv               버전별 지표 한 줄씩
  rules.md                  규칙 원장 — 도입 시점, 담당 지표, 채점 이력
  verify-log.tsv            사람 검증 결과 pass/fail
  reports/v<버전>.md         버전별 보고서
CLAUDE.md                   규칙 본문 (AI가 매 세션 읽는다)
```

## 한 바퀴

보고서는 지표 모음이 아니라 **하네스의 변경 이력과 그 근거**다. 매 절의 주어가
하네스다.

```
릴리스 (MINOR 이상) → git tag → 지표 추출
   │
   ├─ 1. 적용돼 있던 하네스가 무엇이었나
   │        있던 것 / 언제부터 / 실제로 지켜졌나
   │
   ├─ 2. 그게 어떻게 작동했나
   │        규칙별 판정 ← 지표는 여기서 증거로만 등장
   │
   ├─ 3. 무엇이 부족했나
   │        구멍마다 "→ 필요한 것:" 한 줄로 끝낸다
   │
   ├─ 4. 그래서 이렇게 바꿨다
   │        3절 구멍과 1:1 대응. 대응 안 되면 근거 없는 변경이다
   │
   └─ 5. 기대 결과
            지표별 목표 + 성공·실패 판정법
            │
            └─→ CLAUDE.md 갱신 → 다음 버전 2절에서 채점
```

**읽고 나서 `CLAUDE.md`가 안 바뀌면 그 보고서는 쓸 이유가 없었다.**

절차는 [`/report`](../../.claude/skills/report/SKILL.md) 스킬에 있다.

## 두 가지 원칙

**하나. 채점할 수 없는 규칙은 넣지 않는다.**
담당 지표가 없으면 효과를 알 수 없고, 효과를 모르면 문서는 계속 늘고, 늘어난 문서는
아무도 안 읽고, 안 읽히는 문서는 규칙이 아니라 장식이다. 절차가 필요하지만 채점할 수
없는 것은 규칙이 아니라 스킬로 넣는다.

**둘. 정확한 정의보다 안 바뀌는 정의가 낫다.**
지표 정의는 노이즈를 품고 있다. 그래도 버전마다 같기만 하면 노이즈도 같은 크기로
들어가므로 추세는 살아 있다. 정의를 고치면 그 순간 이전 버전과 비교가 끊긴다 —
고쳐야 하면 스키마를 올리고 전체를 다시 돌린다.
