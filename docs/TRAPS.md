# 함정

한 번씩 크게 시간을 쓴 것들. 해당 영역을 건드리기 전에 읽는다.
새로 하나 배우면 여기에 **증상 → 원인 → 대처** 순으로 덧붙인다. 증상부터 적는 이유는,
다음에 이 문서를 찾을 때 손에 있는 건 원인이 아니라 증상뿐이기 때문이다.

## 캘린더: 달을 넘길 때 프레임이 떨어진다

**증상** 스와이프로 달을 이동할 때 눈에 보이는 프레임 드랍. 실기기에서 더 뚜렷하다.

**원인** `CalendarScreen`이 `@Query`로 할 일을 직접 들고, 반복 일정을 펼치고, 재계산
키를 computed property로 만들었다. 할 일 하나가 바뀌거나 달만 넘겨도 화면 전체 body가
다시 돌면서 그 계산이 프레임 안으로 들어왔다. SwiftUI의 `TabView`/`ScrollView`
페이징으로는 이 비용을 감출 수 없었다.

**대처** 세 가지를 분리했다. 이건 취향이 아니라 이 화면이 성립하는 조건이다:

| 역할 | 담당 | 깨면 생기는 일 |
|---|---|---|
| 데이터 계산 | `CalendarSnapshotStore` (백그라운드, 스냅샷) | 계산이 프레임 안으로 돌아온다 |
| 페이징 | `MonthPagerView` (= `UIScrollView`) | 페이징 감각과 프레임이 같이 무너진다 |
| 터치 | `MonthPageInteractionLayer` | 날짜 히트박스가 숫자 주변으로 쪼그라든다 |

지키는 규칙:

- **`CalendarScreen`의 body에서 할 일을 관찰하지 않는다.** `@Query`는 리프 하나에
  가둔다. 여기에 `@Query`를 다시 올리면 5일치 작업이 원위치한다.
- **페이저 자신의 프레임을 재서 되먹이지 않는다.** `topChromeHeight`는 압축
  애니메이션과 무관하게 안정적이어야 한다. 되먹이면 접히는 매 프레임마다 페이지가
  다시 그려진다.
- **하루치 화면은 `navigationDestination`으로 밀어 넣는다.** 한 화면이 달 격자와 주간
  스트립 두 모습을 오가게 만들지 않는다 — 지금 보는 게 뭔지 헷갈리고, 뒤로 가는 길을
  직접 만들어야 하고, 그 전환 애니메이션에 며칠이 들어간다. 이미 해봤다.

**교훈** 이 문제는 감으로 발견했지만 감으로 닫을 수 없었다. "아직 안 매끄러워"가
6번 반복된 뒤 설계를 다시 했다. 다음에 성능 얘기가 나오면 먼저 측정한다
(`CLAUDE.md` R4).

### 이 앱에서 프레임을 먹었던 것들

새 원인을 찾기 전에 여기부터 본다. 지금까지 실제로 원인이었던 것이 전부 여기 있다.

| 원인 | 증상 | 확인법 |
|---|---|---|
| 화면 상위 body에서 `@Query` 관찰 | 데이터 하나 바뀌어도 화면 전체 재계산 | `@Query`가 리프에 있는지 |
| 뷰 프레임을 재서 상위로 되먹임 | 애니메이션 중 매 프레임 재구성 | `GeometryReader` → `@State` 경로 |
| computed property에 계산 | body 돌 때마다 재계산 | 반복 일정 펼치기, 재계산 키 |
| SwiftUI 페이징 | 페이징 감각과 프레임 동시 붕괴 | `UIScrollView`로 내려갔는지 |
| 셀에 `glassEffect` | 목록 길어질 때 저하 | 셀·카드는 불투명 표면 |

계측은 `OSSignposter`로 의심 구간을 감싼다. 프레임 문제는 **매번 실기기에서만** 제대로
드러났다 — 시뮬레이터 프레임은 참고가 안 된다.

성능 작업은 여러 방법을 시도하게 되고 그 잔해가 남았던 적이 있다. 시도가 실패하면
되돌린다. 커밋에 남는 것은 통한 것 하나여야 한다.

## 튜토리얼 오버레이: 그려지는데 눌리지 않는다

**증상** 전체 화면 오버레이(튜토리얼 마스크)의 버튼을 눌러도 아무 일도 일어나지 않는다.

**원인** iOS 26 + 이 앱의 UIKit 생명주기(SceneDelegate + UIHostingController)에서,
`RootTabView`의 `ZStack`에 형제로 얹은 오버레이는 그려지기는 하지만 터치를 받지
못한다. TabView(UIKit 백업)가 화면 전체의 히트 테스트를 먼저 가져간다.

**대처** 앱 창 위에 `UIWindow`(level `.normal + 1`)를 하나 더 올린다 —
`Mosco/App/Common/Tutorial/TutorialOverlayWindow.swift`. 그 창의 `hitTest`가 구멍
안쪽에서 nil을 돌려주면 그 자리의 터치만 아래 앱으로 내려간다.

**그 창은 반드시 `canBecomeKey`를 false로 덮어쓴다.** 안 그러면 키 창이 오버레이로
넘어가서, 아래 앱에서 편집 중이던 `TextField`가 커서만 깜빡이고 글자는 안 써진다.

**같이 나온 것** 오버레이 버튼이 "글자 위에서만" 눌리는 문제는 히트 영역이 텍스트에만
잡혀 있던 것이다. 버튼 영역에 `contentShape`를 준다.

## 위젯이 실행되지 않는다

**증상**
```
Please specify the widget kind in the scheme's Environment Variables
using the key '_XCWidgetKind' to be one of: 'MoscoCalendar','MoscoTodayTodo'
```

**대처** 위젯을 여러 kind로 두면 스킴이 어느 걸 띄울지 모른다. `MoscoWidget` 스킴의
Run > Arguments > Environment Variables에 `_XCWidgetKind`를 넣고 값을 위젯 kind 중
하나로 지정한다. 디버깅 대상을 바꿀 때마다 이 값을 바꾼다.

## Firebase 애널리틱스: DebugView에 아무것도 안 잡힌다

세 가지가 전부 맞아야 잡힌다. 하나만 틀려도 조용히 아무 일도 일어나지 않는다.

1. **Firebase 프로젝트에 Google Analytics가 연결돼 있어야 한다.** 안 돼 있으면
   `GoogleService-Info.plist`에 `MEASUREMENT_ID`가 없다. 콘솔 > 프로젝트 설정 >
   통합에서 켜고 plist를 다시 받는다. **plist에 `MEASUREMENT_ID`가 있는지부터 본다.**
2. **번들 ID가 맞아야 한다.** 위젯용 plist(`com.Mosco.App.MoscoWidget`)를 앱 타깃에
   넣으면 경고만 뜨고 로깅은 안 된다. 앱 타깃은 `com.Mosco.App`.
3. **DebugView는 실행 인자가 필요하다.** `-FIRDebugEnabled`. 스킴에 넣는다.
   이건 심사·릴리스와 무관하다 — 릴리스 빌드는 인자 없이도 정상 로깅된다.

**하지 말 것** 로깅이 안 잡힌다고 UserDefaults 플래그나 우회 코드를 얹지 않는다.
원인은 항상 위 셋 중 하나다. 얹었던 코드는 결국 다 걷어냈다.

## 버전 올리기: pbxproj에 네 곳이 있다

`MARKETING_VERSION`과 `CURRENT_PROJECT_VERSION`이 각각 **네 곳**에 있다
(App · MoscoWidget × Debug · Release). 익스텐션 버전이 앱과 다르면 업로드가 거부된다.

```bash
grep -n "MARKETING_VERSION\|CURRENT_PROJECT_VERSION" Mosco/Mosco.xcodeproj/project.pbxproj
```

빌드 번호는 심사에 올린 빌드마다 1씩 올리고, 버전이 바뀌어도 되돌리지 않는다.
자세한 건 `RELEASING.md`.

## 라이브 액티비티 / 다이나믹 아일랜드: 저절로 시작되지 않는다

**증상** 30분 뒤 일정을 만들고 앱을 백그라운드로 두면, 시간이 돼도 다이나믹
아일랜드에 안 뜬다.

**원인** 라이브 액티비티는 앱이 시작해야 한다. 예정 시각에 저절로 뜨게 하려면
`pushToStartToken`(iOS 17.2+)으로 **서버가** 원격 시작을 밀어줘야 한다. 서버는 넣지
않기로 했다.

**대처** 사용자가 할 일을 꾹 눌러 직접 시작한다. 라이브 액티비티는 최대 8시간이므로,
8시간 넘게 남은 일정은 시작할 수 없다고 알린다.

**표기 규칙** (여러 번 되돌아온 부분)
- 최소 상태: 카테고리 색 + 남은 시간. `+`/`-` 부호를 쓰지 않는다.
  4시 28분에 4시 30분 일정이면 `-1분`이 아니라 `2분 전`.
- 시간이 정해진 일정이 진행 중일 때만 "진행 중". 종료 시각이 없는 일정을 계속
  진행 중으로 두지 않는다.
- 종료 시각이 없으면, 30분 내 다음 일정이 있을 때만 그 일정까지 남은 시간을 띄운다.
  없으면 최소 상태에 아무것도 안 띄운다.
- 확장 상태: 완료 버튼 + 메모 내용. 다음 일정 정보는 넣지 않는다.

## 카테고리 자동 분류: 기준선이 없다

`EmbeddingCategoryClassifier`는 카테고리별 centroid와 코사인 유사도를 비교하고
`similarityThreshold = 0.35`로 자른다. **이 0.35에는 근거 데이터가 없다.**

- 예전에 Create ML 우선순위 분류기를 만들다 버렸다(2026-07-30). 그때의 학습
  데이터와 `.mlmodel`은 2026-08-19에 지웠다 — 남길 값어치는 파일이 아니라
  갈아탄 이유였고, 그건 [`docs/CATEGORIZATION.md`](CATEGORIZATION.md)에 있다.
- 검증은 지금까지 한 문장씩 직접 넣어보는 방식이었다("면접을 넣었는데 should가
  나왔어"). 그래서 임계값이나 centroid 계산을 바꿨을 때 좋아졌는지 나빠졌는지 알 수 없다.
- 분류 로직을 만질 일이 생기면, 만지기 전에 입력–기대 카테고리 쌍 30개 정도를
  적어두고 그 통과 개수를 비교한다. 없으면 바꾸지 말고 이 사실을 먼저 말한다.

## 증상이 그대로면, 고친 코드가 화면에 있는지부터 의심한다

2026-08-22에 "스와이프 삭제가 안 된다"를 **세 번 연속 헛짚었다.** `swipeActions`를
명시하고, `editMode`를 진짜 바인딩으로 바꾸고, List에 얹힌 컨테이너 제스처를
걷어냈는데 증상이 한 번도 안 바뀌었다. 원인은 **시간표 모드였다** — 스와이프
삭제는 List 기능이고 그때 화면에 있던 것은 List가 아니었다.

- `DayViewMode`는 `@AppStorage` **하나를 하루치 페이지와 오늘 할 일 탭이 공유한다.**
  한쪽에서 시간표로 바꾸면 다른 쪽도 시간표다. "두 화면 다 안 된다"는 두 화면이
  같이 고장 났다는 뜻이 아니라 **두 화면이 같은 모드였다**는 뜻이었다.
- 고친 뒤 증상이 **똑같으면** 그건 고칠 곳을 못 찾은 게 아니라 **그 코드가 안
  돌고 있다는 신호**다. 다음 가설을 세우기 전에 그 경로가 실행되는지부터 찍는다.
- 로그 한 줄이 추측 세 번보다 쌌다. `[스와이프]`가 한 줄도 안 찍혔다는 사실이
  곧 답이었다. AI가 시뮬레이터를 못 여는 자리에서는 **탐침을 심어 사람에게 실행을
  부탁하는 것**이 다음 수단이다(R2를 어기지 않는다).

## 맥과 iOS는 entitlements 파일을 같이 쓰지 않는다

Mac App Store는 **앱 샌드박스**(`com.apple.security.app-sandbox`)를 요구하는데,
그건 맥에만 있는 키다. 한 파일에 몰아넣으면 iOS 빌드의 프로비저닝 프로파일과
어긋날 자리를 만든다.

`CODE_SIGN_ENTITLEMENTS[sdk=macosx*]`로 SDK마다 다른 파일을 물린다 —
`App-Mac.entitlements`는 `App.entitlements`에 샌드박스·네트워크·위치 키를 더한
것이고, 위젯도 같은 방식으로 하나 더 있다. **위젯 익스텐션도 따로 샌드박스를
켜야 한다** — 앱만 켜면 맥에서 익스텐션이 걸린다.

맞게 들어갔는지는 파일이 아니라 **서명된 산출물**로 확인한다. 빌드 설정을
잘못 걸어도 빌드는 통과하기 때문이다.

```bash
codesign -d --entitlements :- <경로>/App.app
```

같은 방법으로 2026-08-22에 두 가지를 확인했다 — 맥 프로비저닝이 이미 발급돼
있다는 것(`application-identifier`에 팀 접두사가 붙어 있었다), 그리고 앱 그룹은
맥에서도 iOS 형식(`group.com.Mosco.App`) 그대로 쓴다는 것(맥에서는 팀 접두사가
필요한 경우가 있어 의심했는데 Catalyst는 아니었다. `~/Library/Group Containers/`에
그 이름으로 실제 폴더가 있다).
