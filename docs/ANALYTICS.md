# 분석 데이터 읽는 법

GA4 보고서를 열었을 때 **그 줄이 앱의 어디인지** 알기 위한 문서다. 이름들은
`snake_case`에 추상적이라, 코드를 모르면 `memo`와 `event_schedule`이 같은 화면인지
다른 화면인지도 알 수 없다. 정의는 코드에 있고(`Shared/Analytics.swift`,
`Shared/AnalyticsScreen.swift`), 여기는 **읽는 쪽**을 위한 지도다.

## 화면 이름은 어디서 정해지나

`AnalyticsScreen` 열거형의 rawValue 하나다. 여기 없는 화면은 아예 안 보낸다.
보내는 모양은 이벤트 이름 `screen_view`에 `firebase_screen`과
`firebase_screen_class` 두 파라미터를 **같은 값으로** 싣는 것이다. 둘 다 보내야
GA4의 "페이지 및 화면" 보고서에 제대로 들어간다 — 하나만 보내면 "클래스는 있는데
이름이 없는 화면"으로 잡힌다.

이름을 붙이는 자리는 둘이다. 일반 화면은 뷰에 `.logScreen(.xxx)`를 달고, 탭 둘은
`RootTabView`가 선택이 바뀔 때 직접 센다. 탭은 한 번 세워지면 앱이 떠 있는 동안
계속 살아 있어서 `task`가 다시 안 돌고, 그래서 `logScreen`으로는 실행당 한 번밖에
못 센다.

| 로그에 뜨는 이름 | 실제로 어디인가 |
|---|---|
| `calendar` | 달력 탭. 앱을 열면 여기다 |
| `today` | 오늘 할 일 탭 |
| `day` | 달력에서 날짜를 눌러 **밀려 들어온** 하루 페이지 |
| `settings` | 설정 |
| `calendar_list` | 설정 › 캘린더 목록 |
| `category_list` | 설정 › 카테고리 목록 |
| `search` | 검색 시트 |
| `month_picker` | 달 고르기 시트 |
| `category_editor` | 카테고리 만들기·고치기 시트 |
| `calendar_editor` | 캘린더 만들기·고치기 시트 |
| `memo` | 할 일 상세 시트. 이름이 `memo`지만 메모만 있는 화면은 아니다 |
| `event_schedule` | 날짜·시간 고르기 시트 |

**`today`와 `day`는 같은 화면이다**(`DayTodosContentView`). 일부러 둘로 나눠
센다 — "되살린 탭이 쓰이는가"와 "달력에서 날짜를 눌러 들어오는가"는 다른 질문이고,
한 이름으로 묶으면 어느 쪽도 답이 안 나온다. 어느 문으로 들어왔는지는 `day_opened`가
따로 센다.

확인창, 길게 누르기 메뉴, 안내 오버레이, 입력창은 화면으로 세지 않는다. 사람이
"다른 곳에 왔다"고 느끼는 자리만 센다.

## 이름을 바꾸지 않는다

화면 이름도 이벤트 이름도 한 번 정하면 바꾸기 어렵다. 바꾸는 순간 그 전 데이터와
이어지지 않아서 보고서에 같은 것이 두 줄로 나온다. 이름이 안 읽히면 이름을 고치지
말고 **이 문서를 고친다.**

(예외가 한 번 있었다. `complete_task` → `todo_completed`는 일부러 끊었다 — 앱
경로에서 `completed`가 뒤집혀 기록되던 버그가 오래 있어서, 한 지표 안에 반대 뜻의
값이 섞여 되살릴 수 없었다.)

## 기기에서 바로 읽기

GA4는 하루쯤 지나야 보이고 DebugView는 따로 켜야 한다. "지금 어느 화면으로
세어졌나"는 기기를 들고 눌러보며 확인하는 질문이라, 화면 이름은 콘솔에도 남긴다.

Console.app에서 subsystem `com.Mosco.App`, category `screens`로 거르면
`화면 → today`가 실시간으로 찍힌다. **릴리스 빌드에서도 남는다.**

## 숫자를 볼 때 먼저 봐야 하는 것

**어느 버전에서 온 데이터인가.** 2026-10-08 기준 지난 28일 활성 사용자의 다수가
아직 1.2.0이었다. 그래서 이런 일이 생긴다.

- `category_suggested`가 전체 이벤트의 **절반**(6,229건)인데 `todo_created`는
  876건이다. 1.3.1 전에는 타이핑이 멈출 때마다 남겼고, 그때 평균이 할 일 하나당
  7.7번이었다. 지금 비율이 7.1이다 — **거의 전부가 옛 버전에서 온 것**이다.
  지금 코드는 저장할 때 한 번만 남긴다(`CategorySuggestionLog`).
- `analytics_identity`가 405건 / 사용자 74명이다. 지금 코드는 설치마다 한 번만
  남기지만, 1.3.1 전에는 실행마다 남겼다.
- `screen_view`는 434건 / 사용자 37명뿐이다. 화면 로깅이 1.4.x에 들어갔으니
  옛 버전 사용자에게는 아예 없다. **화면 데이터가 적은 것은 버그가 아니라
  업데이트가 아직 안 퍼진 것이다.**

**디버그 빌드는 보내지 않는다.** `FirebaseAnalyticsSink.shouldSend`가 막는다 —
개발 중 시뮬레이터 실행이 전부 실사용자로 잡혀서 다운로드 3회인 앱의 활성 기기가
10대 넘게 잡힌 적이 있다. DebugView로 확인해야 할 때만 실행 인자
`-MoscoFirebaseSend`로 그때만 켠다.

**개발자 기기를 뺀다.** `internal_user = true`를 걸러야 실제 사용자 숫자다.
표시는 그 기기에서 `mosco://internal`을 한 번 열어 켠다(끄려면 `.../off`).
기기 id는 설정 화면에 뜬다 — 보고서의 한 줄과 손에 든 기기를 그걸로 맞춘다.

## 맞춤 측정기준을 등록해야 보인다

GA4는 **등록하지 않은 이벤트 파라미터를 보고서에서 보여주지 않는다.** 그리고
등록은 지난 데이터에 **소급되지 않는다.**

지금 등록이 안 돼 있어서 못 읽고 있는 것들이다. 관리 › 맞춤 정의에서 등록한다.

- `origin` (`analytics_identity`) — 재설치를 건너오는 비율. 이걸 재려고 만든
  이벤트인데 지금껏 한 번도 읽을 수 없었다
- `device_id`, `device_model`, `internal_user` — 사용자 범위와 이벤트 범위 **둘 다**.
  사용자 범위만으로는 기기를 못 가른다(아래)
- `source`, `completed` (`todo_completed`) — 위젯을 계속 만들지 정하는 근거
- `from`, `is_today` (`day_opened`) — 오늘로 들어오는 문

## 사용자 단위와 기기 단위는 다르다

사용자 식별자(`analyticsUserID`)는 **iCloud로 기기를 건넌다.** 아이폰과 맥을 같이
쓰는 한 사람은 한 사람으로 세어진다 — 그게 이 설계의 목적이다.

그래서 **기기를 가르는 일은 user property로 할 수 없다.** GA4의 user property는
사용자 하나당 값 하나라, 아이폰 한 대를 내부로 표시하면 그 사람의 맥에서 온
이벤트까지 함께 빠진다. 기기별로 보려면 **이벤트 파라미터** 쪽 `device_id`를 쓴다.
