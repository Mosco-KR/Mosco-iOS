# 카테고리 자동 분류

한 줄로 적은 할 일에 카테고리를 자동으로 붙인다. `저녁 운동하기`를 치면 '운동'이
붙는 그 기능이다.

구현은 [`EmbeddingCategoryClassifier`](../Mosco/App/Common/ML/EmbeddingCategoryClassifier.swift)
하나에 들어 있다.

## 어떻게 도는가

**학습이 없다.** 미리 훈련시켜 둔 모델을 들고 다니는 것이 아니라, 사용자가 이미
만들어 둔 데이터로 그때그때 계산한다.

```
입력 제목
   │
   ├─ 1. 임베딩 경로 (기본)
   │     제목 → 단어 벡터 평균 → 문장 벡터
   │     카테고리마다: 그 안에 든 할 일 제목들의 평균 벡터(centroid)
   │     코사인 유사도가 제일 높은 카테고리를 고른다
   │     0.35 미만이면 아무것도 고르지 않는다
   │
   └─ 2. 어휘 겹침 경로 (대체)
         공백을 지운 뒤 부분 문자열로 겹치는지만 본다
         "운동" ⊂ "저녁운동하기" → '운동'
```

### 왜 두 경로인가

1번이 못 도는 경우가 있다. `NLEmbedding.wordEmbedding(for: .korean)`이 **`nil`을
낼 수 있다** — Apple이 온디바이스로 지원하는 언어 목록은 OS와 기기에 따라 다르고
계속 바뀐다. 그 한 줄 때문에 기능이 통째로 죽으면 안 되므로, 임베딩이 없거나 유사도가
전부 낮으면 2번으로 내려간다.

2번이 정확한 토큰 일치가 아니라 **부분 문자열 포함**인 것은 한국어 때문이다.
조사가 붙어서 `운동` → `운동하기` → `운동할까`로 늘어나는데, 토큰을 정확히 맞추려
들면 이 흔한 경우를 놓친다.

### 콜드스타트

카테고리를 방금 만들어 아직 아무 할 일도 안 담겼으면 비교할 제목이 없다. 그래서
**카테고리 이름 자체**를 비교 대상에 넣는다. '운동'이라는 이름만으로도 첫 추천이
된다.

### 임계값 0.35에는 근거가 없다

솔직하게 적어둔다. **이 숫자는 몇 번 넣어보고 정한 값이고 데이터가 없다.**
바꿨을 때 좋아졌는지 나빠졌는지 잴 방법이 지금 없다.

분류 로직을 만질 일이 생기면 **만지기 전에** 입력–기대 카테고리 쌍 30개를 먼저
적어두고 그 통과 개수를 비교한다. 그게 없으면 바꾸지 말고 이 사실을 먼저 말한다.
([`docs/TRAPS.md`](TRAPS.md), [`docs/BACKLOG.md`](BACKLOG.md)에도 같은 내용이 있다.)

## 왜 Core ML을 버렸나

처음에는 **Create ML로 학습시킨 텍스트 분류기**였다. 2026-07-30에 갈아탔다.

그때 만든 것:

- `MoscoML.mlproj` — Create ML 프로젝트, `.mlmodel` 두 개 (1.4MB)
- `MLTraining/priority-training-data.csv` — 제목–라벨 354행, 클래스당 85~97개
- 라벨은 MoSCoW 우선순위 넷: `must` / `should` / `could` / `wont`

**둘 다 저장소에서 지웠다** (2026-08-19). 남길 값어치가 있는 것은 파일이 아니라
아래 이유였고, 그건 이 문서에 있다. 되살릴 일이 생기면 git 이력에 있다.

### 이유 1 — 분류 대상이 바뀌었다

Create ML 분류기는 **우선순위**(must/should/could/wont)를 맞히는 것이었다. 그런데
우선순위 자체를 걷어내고 **사용자 정의 카테고리**로 바꿨다. 넷으로 고정된 라벨을
맞히는 모델은 "사용자가 방금 만든 '병원' 카테고리"를 영원히 모른다.

이게 결정적이었다. 나머지 이유는 이 결정을 따라온 것이다.

### 이유 2 — 학습된 모델은 사용자를 못 따라간다

Create ML 모델은 빌드 시점에 고정된다. 카테고리를 추가하려면 데이터를 모으고,
다시 학습시키고, 앱을 다시 심사받아 내보내야 한다. **사용자가 카테고리를 하나
만드는 데 앱 업데이트가 필요한 구조**다.

지금 방식은 카테고리를 만들고 할 일을 하나 넣는 순간 다음 추천에 반영된다.
사용자가 태그를 고르는 행위 자체가 곧 학습이다.

### 이유 3 — 무게

`.mlmodel` 두 개가 1.4MB였다. 온디바이스 임베딩은 OS가 들고 있는 것을 빌려 쓰므로
앱 번들에 더해지는 것이 없다.

### 무엇을 잃었나

정직하게 적으면 **정확도를 재는 방법**을 잃었다. Create ML은 학습할 때 검증 정확도를
숫자로 내준다. 지금 방식에는 그런 숫자가 없고, 그래서 임계값 0.35에 근거가 없는
상태가 됐다. 위의 "기준선 30쌍"이 그 자리를 메우려는 것이다.
